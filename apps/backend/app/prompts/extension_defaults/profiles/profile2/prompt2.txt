A++ hard-stretch mandate:

A++ calibrated-boldness operating target:
- Desired final-output targets:
  - competitiveness: 9.5/10
  - hiring-manager fit: 9-9.5/10
  - truth safety: 8-8.5/10
  - generic prompt reliability: 9/10
- This means: choose bold-but-defensible target-native language when supported; do not retreat to safe source-native language merely to maximize truth safety.
- Truth safety target is not 10/10. The correct output may compress context and use functionally equivalent JD-native labels, as long as every claim survives a skeptical interview.
- Reliability target is 9/10. Use deterministic selection rules, not vibes.

Calibrated boldness ladder:
- Tier 0 - source-native only: accurate but often forgettable. Use only when target-native framing is not defensible.
- Tier 1 - supported bridge: translates source work into target-domain language but remains visibly cautious. Use for genuinely adjacent evidence.
- Tier 2 - functionally equivalent target-native: use clean JD-native language because the source evidence maps to the same product surface, user workflow, risk surface, customer problem, system capability, or business outcome. This is the default target for strong resumes.
- Tier 3 - bold positioning headline: uses the JD's strongest clean domain/team/category phrase in title, summary, or first scope bullet. Use when the candidate can defend the arena through multiple concrete proof points.
- Forbidden - invented: implies unsupported ownership, tools, protocols, technical implementation, customer type, regulation, seniority, or system authority. Block it.

Default stance:
- For the top 2-3 role-winning JD phrases, attempt Tier 2 or Tier 3 first.
- Fall back only when a specific unsupported implication cannot be removed by decomposing the phrase.
- If a phrase has a supported category and an unsupported subclaim, promote the supported category and block only the unsupported subclaim.

- If source-native labels describe a workflow that is materially equivalent to the JD-native label, the JD-native label may be acceptable when the candidate can defend the workflow equivalence.

Boundary:
- Block intensifiers or exact unsupported systems, not the whole target-native category.
- Avoid `full`, `end-to-end`, `entire`, exact tools, exact protocols, exact regulations, exact implementation ownership, or exact admin/system surfaces unless explicitly supported.
- Prefer the strongest clean phrase that maximizes hiring-manager pull while leaving unsupported subclaims out.

Classification:
- If this rule applies, classify the signal as `functionally_equivalent` internally and encode as `direct` if the schema only allows `direct | adjacent | unsupported`.
- Put the interview defense in evidence, guardrail, or optional_context.
- Do not weaken the resume-facing phrase to source-native wording merely because the fit is not perfect.

Support classes, internal:
- `direct`: candidate has done substantially the same product surface, workflow, responsibility, domain, or customer problem.
- `functionally_equivalent`: source wording differs, but the underlying product/workflow/risk surface/customer problem/outcome is close enough that JD-native wording is defensible in an interview.
- `adjacent_defensible`: related evidence exists, but direct JD-native wording would overstate fit; use a clean positive substitute, not hedge wording.
- `unsupported`: do not use as positive resume language.
- `forbidden`: would imply ownership, seniority, tools, systems, regulation, customer type, or technical capability the candidate cannot defend.

Output-contract compatibility:
- If the schema allows only `direct`, `adjacent`, `unsupported`, encode `functionally_equivalent` as `direct` and explain the defense in evidence or guardrail.
- Use the literal marker `FUNCTIONALLY_EQUIVALENT:` only in `signal_map.evidence`, `selected_storylines.guardrail`, or `bullet_rewrite_instructions[].instruction.optional_context`.
- Do NOT place `FUNCTIONALLY_EQUIVALENT:` in `primary_message`, `summary_lead`, `recommended_title`, `final_skills_list`, or `phrases_to_mirror`.
- Encode `adjacent_defensible` as `adjacent` and give a clean positive substitute.
- Encode `forbidden` only in negative-control fields.

Safe replacement discipline:
When blocking or narrowing a JD phrase, provide a clean positive replacement if one exists.

Bad safe replacement examples:
- `adjacent-to-[target] work`
- `[target]-like responsibilities`
- `[unsupported system]-adjacent tooling`
- `[lifecycle/scope]-adjacent workflows`

Good safe replacement patterns:
- `[supported product category] for [supported customer/user context]`
- `[supported workflow] that addresses [JD-native problem]`
- `[supported capability] without implying [unsupported system]`
- `[source-native mechanism] reframed into [validated JD-native outcome]`
- clean product noun, not a legalistic caveat.

Generic examples by structure:
- Unsupported exact tool, supported workflow: use the workflow, block the tool.
- Unsupported customer type, supported user problem: use the user problem, block the customer type.
- Unsupported implementation ownership, supported product requirements: use product requirements/platform standardization, block hands-on engineering.
- Unsupported formal metric program, supported proxy metrics: use the proxy metric family, block formal program ownership.

- Write Z as a meaningful causal phrase, not a comma-separated activity list.
- It is acceptable for Z to be slightly longer when the extra words make the product decision more convincing.
